# Q-Before-A — Question Before Answer

## Overview

强制工作模式：**先澄清，后执行**。一旦检测到触发词 `请澄清`，立即进入"澄清模式"：先完整读取所有上下文（尤其是上传的文件），再逐条拆解用户需求，最后以编号列表的形式一次性提出所有关键疑问，**在用户明确确认前不得执行任何具体任务**。

## When to Use

当用户消息中包含触发词 `请澄清` 时，必须使用本 Skill。可同时存在其他意图词（如「帮我做 X」「请澄清」），只要「请澄清」出现即生效。

## Workflow Decision Tree

```
检测到 "请澄清"
    │
    ├─ 1. 进入澄清模式（不再执行任何写文件/运行命令/调用工具的具体任务）
    │
    ├─ 2. 收集上下文
    │     ├─ 检查是否有上传的文件/图片/附件 → 用 Read 等工具完整读取
    │     └─ 回顾当前对话已有信息
    │
    ├─ 3. 拆解需求
    │     └─ 把用户请求拆成 N 条独立需求点，逐条审视
    │
    ├─ 4. 找疑点
    │     ├─ 模糊表述（含义不清、有多种解读）
    │     ├─ 缺失信息（关键参数未给）
    │     ├─ 互相冲突（需求之间或与上下文冲突）
    │     └─ 边界不清（范围、格式、长度、风格等未指定）
    │
    ├─ 5. 输出澄清问题
    │     └─ 简洁友好的编号列表，一次性提出全部疑问
    │
    └─ 6. 等待用户确认 → 用户回复后再切换回正常执行模式
```

## Step 1 — Enter Clarification Mode

检测到 `请澄清` 后：

- **立即停止**任何正在进行的具体执行（写文件、运行命令、修改代码等）。
- 在内部切换为"只读 + 提问"模式。
- 不要猜测用户意图来提前执行；不要为了"看起来在做事"而先做一步再说。

## Step 2 — Read All Context Completely

- 如果消息中包含**上传的文件**（图片、PDF、代码、文档、表格等），使用 `Read` 工具**完整读取**，不要跳过或只读摘要。
- 如果有多个文件，**逐个全部读完**。
- 如果文件较大需要分段，使用 `offset` + `limit` 多次读取直到读完为止。
- 读取完毕后在心中形成对每个文件内容的清晰摘要，便于后续与用户需求对照。

## Step 3 — Decompose the Request

- 把用户消息中提到的所有要求拆成**独立的需求点**，每点一行。
- 每个需求点包含三要素：**目标 / 范围 / 验收标准**（如果用户没给就标记为疑点）。
- 不要把多个需求合并成一条；明确区分"必须做"和"可选/锦上添花"。

## Step 4 — Identify All Gaps

针对每条需求点和每份文件，逐项检查：

| 类型 | 表现 | 提问方向 |
|------|------|----------|
| 模糊 | "做得好看一点" "风格合适" | 给具体标准 / 给出示例 |
| 缺失 | 没说字数 / 没指定输出格式 / 没给时间范围 | 明确给出参数 |
| 冲突 | 两条需求互相矛盾 | 让用户二选一或加权 |
| 边界 | "所有文件" "完整数据" | 限定范围 |

把找到的所有疑点**全部收集**，不要在提问前就自己挑着问。

---
🔴 **CHECKPOINT · 需求拆解暂停**：已完成需求拆解，共识别出 **N 个疑点**。请向用户确认：
- 已拆解的 N 条需求是否完整？有无遗漏？
- 识别的疑点是否准确？有无多余或缺失？
**确认后再进入疑点输出阶段（Step 5）**，不得跳过。

---

## Step 5 — Output the Clarification List

**一次性**输出所有问题，使用**编号列表**，格式参考：

```
收到 ✅ 我已读完所有上传文件（<N> 个）和你的全部需求，先不执行，先跟你对齐几个关键点：

1. **关于 <主题>**：<你的疑问，一句话>
2. **关于 <主题>**：<你的疑问，一句话>
3. ...

确认这些之后我再开始动手。你可以直接回答编号，也可以补充更多细节。
```

要求：

- **简洁友好**：每条疑问不超过 1–2 句话，冗长解释放到确认后的执行阶段。
- **只问关键信息**：过滤以下无关细节——格式/措辞/语气等审美偏好（可自行判断）、明显遵循行业惯例的参数（如PPT 16:9比例）、用户未提及但业界通用的默认值。
- **编号清晰**：用户可以直接回"1 是 X，2 是 Y，3 默认即可"这种格式。
- **不夹带执行**：即使前几步已经"读完了文件"，也不要顺手开始做；澄清模式期间任何产出物都要等用户确认。
- **语气**：温和但不卑微，例如「先跟你对齐几个点」而不是「请允许我冒昧地问」。

---
🔴 **CHECKPOINT · 疑点列表输出确认**：确认已完整读取所有文件、已一次性提出全部疑点（编号列表格式）后，才进入 Step 6。**未确认前不得执行任何具体任务**。
---

## Step 6 — Wait for Confirmation

- 收到用户回复后，**逐条核对**是否所有疑点都已回答。
- 如果仍有未回答的关键点，**再次简短追问**（不要重复整张清单，只点出剩余项）。
- 只有当所有关键点都已确认，**才退出澄清模式**并切换到正常执行流程。
- 用户如果说"按你理解的来"或"默认即可"等豁免性回答，对未涉及的关键点采用合理默认值即可执行。

## 失败模式与兜底

### 场景1：用户长时间不回复
- **触发条件**：发出澄清问题后，用户超过 30 分钟未回复
- **一线处理**：主动提醒一次（"还没收到你的确认，我先暂停等回复"）
- **仍无回复**：结束澄清模式，注明"待用户确认后再执行"

### 场景2：用户回复模糊/敷衍
- **触发条件**：用户回复"随便""你看着办""都可以"等模糊回答
- **一线处理**：默认执行，标注所有关键点均采用默认，格式：「关键点 A/B/C 已采用默认：X」
- **仍不明确**：只追问**高影响力**问题（满足任一即追问）：
  - 影响输出格式（如交付格式/页数/字数）
  - 决定技术选型（如架构方案/数据库选型）
  - 涉及安全或不可逆操作（如删除文件/线上变更/数据迁移）

### 场景3：用户只回答了部分问题
- **触发条件**：用户只回复了清单中部分编号
- **一线处理**：只追问未回答的项，不重复已确认的
- **仍不完整**：其余关键点采用合理默认值，继续执行；标注格式：「✅ 已确认：1=A / 2=B ｜ ⏭️ 未确认项默认：3=C（原因）」

### 场景4：用户明确拒绝回答
- **触发条件**：用户直接说"不用问了，直接做"
- **一线处理**：尊重用户选择，明确告知将使用默认假设
- **仍需谨慎**：高风险任务（删除文件/线上操作等）明确提示风险后执行

## Guardrails — 必须遵守的红线

1. **检测到 `请澄清` → 立即停止执行**，即使前文对话已经进展到一半。
2. **必须完整读完上传文件**，不允许只读摘要或跳过部分内容。
3. **一次性提出全部疑问**，不要挤牙膏式逐条问。
4. **编号列表呈现**，方便用户逐项回复。
5. **未经用户确认前不得执行**，包括但不限于：写文件、运行命令、调用外部工具、生成产物。
6. **不要假装"已经准备好了"，而是要真的停下来等。**

## Examples

### 正确示例

> 用户：请帮我基于这份季度财报写一份董事会汇报 PPT，请澄清。
>
> AI：
> 收到 ✅ 我已读完上传的「2026 Q1 财报.pdf」（共 28 页）和你的需求，先不执行，先跟你对齐几个关键点：
>
> 1. **汇报受众**：是董事会全量成员，还是仅财务委员会？需不需要照顾非财务背景的董事？
> 2. **时长控制**：PPT 打算讲 10 分钟、20 分钟还是 30 分钟？这会决定页数。
> 3. **重点数据**：希望突出营收、利润、现金流中的哪一个？还是三个都要？
> 4. **风格**：公司有没有指定模板？或者用通用商务风格即可？
> 5. **交付格式**：.pptx、.pdf 还是 .key？
>
> 这五点确认后我再开工。

### 正确示例（无上传文件）

> 用户：请澄清。我需要一份用户增长的分析报告
>
> AI：
> 收到 ✅ 已理解你的需求，无上传文件，直接进入澄清。先跟你对齐几个关键点：
>
> 1. **数据范围**：分析的时间区间是什么？（如 2026 Q1、过去30天、自定义区间）
> 2. **用户定义**："用户增长"指新增注册数、活跃用户数、还是付费用户数？
> 3. **分析维度**：需要按渠道/地区/设备类型拆分吗？还是只看整体趋势？
> 4. **输出形式**：Excel 表格、数据透视表、还是文字结论？
>
> 确认后我再开始拉数据。

### 错误示例（不要这样做）

> ❌ 「好的，我先帮你读一下文件……好了，我大致看了一下，下面我先按我的理解写一版给你参考……」
>
> 问题：澄清模式下不应执行写文件等动作，必须先停下来等用户确认。

### 各场景错误示例对照表

| 场景 | ❌ 错误做法 | ✅ 正确做法 |
|------|-----------|-----------|
| 场景1 长时间不回复 | 静默等待超过30分钟什么都不做 | 主动提醒一次"还没收到确认，先暂停等回复"，仍无回复则注明"待确认后执行" |
| 场景2 用户模糊回复 | 直接按模糊回答执行，不标注默认假设 | 默认执行但标注"关键点A/B/C已采用默认：X"，高风险任务追问 |
| 场景3 部分回答 | 重复整张清单要求补全 | 只追问剩余未回答项，不重复已确认的 |
| 场景4 用户拒绝回答 | 不警告直接执行高风险操作 | 尊重选择，明确提示"将使用默认假设X，高风险操作Y请知悉" |

## 🔴 红灯/危险动作反例清单

以下行为**绝对禁止**：

| # | 🔴 红灯行为 | 触发条件 | 正确做法 |
|---|-----------|---------|---------|
| R1 | **挤牙膏式逐条提问** | 分多次提问而非一次性列出 | Step4 找完所有疑点后，Step5 一次性输出全部 |
| R2 | **不读文件就开始执行** | 用户上传了文件但没读完就开始做事 | 必须用 Read 完整读取后才进入澄清 |
| R3 | **用"我觉得/我猜"代替用户决策** | 用户未明确表态时擅自假设 | 标注默认假设并要求确认，或追问高影响力项 |
| R4 | **跳过 CHECKPOINT 直接进入 Step6** | 省略需求拆解暂停确认直接输出问题 | 两个🔴CHECKPOINT必须显式等待用户确认 |
